## 0. เอกสารตั้งต้นและการปรับปรุงให้ตรงกับระบบปัจจุบัน

รายงานฉบับนี้ใช้เอกสารหัวข้อปริญญานิพนธ์ **Agentic GraphRAG System for Semiconductor Stock** เป็นจุดตั้งต้น แล้วปรับรายละเอียดให้ตรงกับระบบและผลทดลองที่มีอยู่จริงในปัจจุบัน การปรับเช่นนี้จำเป็น เพราะเอกสารหัวข้ออธิบาย “ระบบที่ตั้งใจจะพัฒนา” ส่วนรายงานความก้าวหน้าต้องอธิบาย “ระบบที่พัฒนาและตรวจสอบแล้วจริง”

| ประเด็น | แนวคิดในเอกสารตั้งต้น | สถานะปัจจุบันที่ใช้ในรายงานนี้ |
|---|---|---|
| ปัญหาหลัก | Vector RAG เชื่อมข้อมูลหลายทอดได้จำกัด, ข้อมูลมีหลายรูปแบบ และตรวจสอบเส้นทางคำตอบได้ยาก | ยังคงเป็นปัญหาหลักของโครงงาน |
| โครงสร้างข้อมูล | แยกกราฟ ฐานข้อมูลตัวเลข และข่าวตามธรรมชาติของข้อมูล | ทำจริงด้วย Neo4j, PostgreSQL และ News API |
| กราฟความรู้ | ใช้กรอบ FinReflectKG 24 ประเภทของรายการ และ 29 ประเภทความสัมพันธ์ | ใช้เป็นแกน Schema จริงของระบบ |
| การสกัดกราฟ | เดิมวาง GLiNER สำหรับ Entity และ LLM สำหรับ Relation | เส้นทางหลักปัจจุบันใช้ LLM สกัด Entity และ Relation ในการเรียกเดียว พร้อมตรวจด้วย Pydantic; มี Evidence-grounded graph repair หลังการสกัด และ GLiNER ไม่ใช่เส้นทางหลักแล้ว |
| การค้นกราฟ | Personalized PageRank ตามแนวทาง HippoRAG | ใช้งานจริงเป็น Graph Search โดยเชื่อมผลจากรายการในกราฟกลับมาเป็นส่วนข้อความ |
| Agent | เดิมอธิบายเป็น ReAct ร่วมกับ Reflection แยกเป็นรอบ | ปัจจุบันใช้ PlanRoute → Dispatcher → Task Worker → Execute/Assess/Retry → Collector → Synthesis โดยแต่ละงานย่อยแยกสถานะออกจากกันและทำพร้อมกันได้ตามเพดานที่กำหนด |
| การประเมิน | เดิมวางแผนสองชั้นรวมประมาณ 100 คำถาม โดยมี FinanceBench และ FinReflectKG | หลักฐานที่ทำเสร็จและตรึงแล้วคือ SOX74 Retrieval Ablation และ Financial ETL/Financial E2E; Full Agent รวมทุกเครื่องมือยังไม่ใช่ผลสรุปสุดท้าย |
| ข่าว | เดิมกำหนดข่าวย้อนหลัง 6 เดือนแบบเรียลไทม์ | ค่าเริ่มต้นปัจจุบันย้อนหลัง 90 วัน มีตัวเลือก cache สำหรับการทดลอง และยังไม่มี Benchmark หลัก |
| กลุ่มบริษัท | เดิมวางเป้าหมายประมาณ 30 บริษัท | Config ปัจจุบันมี 22 ticker และฐานข้อมูล Production มีเอกสารตามข้อมูลที่ดึงได้จริง |

ดังนั้น รายงานนี้ยังรักษาเหตุผลและแนวคิดวิจัยจากเอกสารตั้งต้น แต่ให้ผลการทดลองและข้อสรุปยึดจาก Code, Config และ Evidence Artifact ปัจจุบันเป็นหลัก

## บทคัดย่อ

โครงงาน SemiGraph มีเป้าหมายในการพัฒนาระบบค้นและรวบรวมหลักฐานสำหรับการวิเคราะห์บริษัทในกลุ่ม Semiconductor โดยเน้นให้ระบบสามารถตอบคำถามจากข้อมูลหลายลักษณะ ได้แก่ ข้อความในรายงานบริษัท ความสัมพันธ์ระหว่างบริษัทกับรายการทางธุรกิจ ตัวเลขทางการเงิน และข่าวสารล่าสุด

แนวคิดสำคัญของโครงงานคือ คำถามแต่ละประเภทไม่ควรใช้วิธีค้นแบบเดียวกันทั้งหมด คำถามที่ถามถึงข้อความหรือข้อเท็จจริงทั่วไปอาจเหมาะกับการค้นด้วยความหมายของประโยค ขณะที่คำถามที่ต้องเชื่อมข้อมูลหลายทอดควรใช้โครงสร้างความสัมพันธ์ และคำถามที่ถามตัวเลขควรค้นจากฐานข้อมูลตัวเลขที่มีสูตรและแหล่งที่มาชัดเจน

จนถึงปัจจุบันได้พัฒนาส่วนหลักของระบบครบถ้วนในระดับใช้งาน ได้แก่ กระบวนการนำเข้าข้อมูลและสร้างกราฟความรู้ ระบบค้นด้วยข้อความ ระบบค้นด้วยกราฟ ระบบค้นข้อมูลทางการเงิน และระบบค้นข่าว นอกจากนี้ยังมีการประเมินระบบค้นด้วยชุดคำถาม FinReflectKG จำนวน 74 ข้อ และประเมินระบบข้อมูลทางการเงินทั้งระดับการนำเข้าข้อมูลและการตอบคำถามแบบครบกระบวนการ

ผลการทดลองที่มีหลักฐานแช่แข็งไว้แล้วพบว่า เมื่อกำหนดจำนวนหลักฐานปลายทางเท่ากันที่ 9 ชิ้น ระบบ Agent + Graph ให้ค่า Hit@9 เท่ากับ 0.743 และ Recall@9 เท่ากับ 0.450 สูงกว่า Graph-only ที่ได้ 0.649 และ 0.390 ตามลำดับ อย่างไรก็ตาม Agent + Graph ใช้เวลาเฉลี่ย 84.196 วินาที ขณะที่ Graph-only ใช้เวลาเฉลี่ย 18.222 วินาที จึงสรุปได้ว่าการเพิ่มชั้น Agent ช่วยเพิ่มโอกาสค้นพบหลักฐาน แต่ยังมีต้นทุนด้านเวลาอย่างชัดเจน

ในส่วนข้อมูลทางการเงิน ระบบพบข้อมูลที่ตรงกับข้อมูลอ้างอิงจาก SEC จำนวน 364 จาก 370 รายการ คิดเป็น 98.38% และค่าหน่วยกับรอบเวลาของรายการที่พบตรงกัน 100% ผลดังกล่าวสนับสนุนว่าแกนกลางของโครงงานมีความพร้อมสำหรับการนำเสนอเชิงวิชาการ ส่วนการประเมินความถูกต้องของการสกัดกราฟ Full Agent และระบบข่าวยังเป็นงานที่ต้องทำเพิ่มเติมก่อนสรุปผลขั้นสุดท้าย

## 1. ที่มาและปัญหา

ข้อมูลสำหรับวิเคราะห์บริษัท Semiconductor ไม่ได้อยู่ในรูปแบบเดียวกันทั้งหมด ตัวอย่างเช่น

1. รายงานประจำปีมีข้อความอธิบายธุรกิจ ความเสี่ยง และนโยบายการจัดสรรค่าใช้จ่าย
2. ข้อมูลบางอย่างต้องเชื่อมโยงหลายขั้น เช่น บริษัท → กลุ่มธุรกิจ → รายการค่าใช้จ่าย → ผลกระทบทางการเงิน
3. ตัวเลข เช่น รายได้ อัตรากำไร และผลตอบแทนต่อสินทรัพย์ ต้องอาศัยสูตรและรอบเวลาที่ถูกต้อง
4. ข่าวมีความเปลี่ยนแปลงตามเวลา จึงต้องมีวันเผยแพร่และแหล่งอ้างอิง

หากใช้วิธีค้นแบบเดียวกับข้อมูลทุกประเภท อาจเกิดปัญหา เช่น ค้นพบข้อความที่มีคำคล้ายกันแต่ขาดความสัมพันธ์ที่จำเป็น ค้นตัวเลขจากข้อความผิดปี หรือสร้างคำตอบที่ไม่สามารถตรวจสอบย้อนกลับไปยังแหล่งข้อมูลได้

ดังนั้น โครงงานนี้จึงมุ่งพัฒนาระบบที่มีวิธีค้นหลายรูปแบบ และจัดเส้นทางการค้นให้เหมาะกับชนิดของคำถาม

## 2. วัตถุประสงค์

วัตถุประสงค์ในเอกสารตั้งต้นมี 4 ส่วน และยังคงเป็นกรอบของโครงงานปัจจุบัน โดยปรับถ้อยคำให้ตรงกับสิ่งที่ทำจริงดังนี้

1. พัฒนาท่อข้อมูลจากรายงาน 10-K ตั้งแต่การดึงข้อมูล การทำความสะอาด การแบ่งส่วนข้อความ การสกัดรายการและความสัมพันธ์ ไปจนถึงการจัดเก็บใน Neo4j โดยใช้ออนโทโลยี FinReflectKG เป็นกรอบ
2. พัฒนาสถาปัตยกรรมจัดเก็บข้อมูลหลายรูปแบบ ได้แก่ Neo4j สำหรับข้อมูลบรรยายและความสัมพันธ์ PostgreSQL สำหรับข้อมูลตัวเลข และ News API สำหรับข้อมูลข่าว
3. พัฒนาวิธีค้นที่เหมาะกับคำถามแต่ละชนิด โดยเฉพาะ Graph Search ที่ใช้ Personalized PageRank เพื่อรองรับคำถามหลายทอด และ Financial Search ที่ใช้ข้อมูลตัวเลขกับสูตรที่ตรวจสอบได้
4. พัฒนา Agent ให้เลือกเครื่องมือ เก็บหลักฐาน ประเมินความเพียงพอ ค้นซ้ำเมื่อมีแนวทางที่มีประโยชน์ และเก็บร่องรอยการทำงานเพื่อการตรวจสอบย้อนหลัง
5. วัดผลระบบเป็นรายชั้น ได้แก่ คุณภาพการค้นหลักฐาน ความถูกต้องของข้อมูลการเงิน และการทำงานของ Agent โดยไม่รวมผลที่ยังไม่ได้ทดลองไว้ในข้อสรุป

## 3. ขอบเขตปัจจุบัน

### 3.1 ข้อมูลและฐานข้อมูล

ระบบมีฐานข้อมูลหลักสองส่วน

| ฐานข้อมูล | หน้าที่ | ข้อมูลที่เหมาะสม |
|---|---|---|
| Neo4j | เก็บข้อความที่แบ่งเป็นส่วนย่อยและความสัมพันธ์ระหว่างรายการ | คำอธิบายธุรกิจ ความสัมพันธ์ และคำถามหลายทอด |
| PostgreSQL | เก็บข้อมูลตัวเลขที่ผ่านการจัดรูปแบบและตรวจสอบ | รายได้ อัตรากำไร การเติบโต และตัวชี้วัดทางการเงิน |

จากการตรวจสอบฐานข้อมูล Production ล่าสุดพบว่า Neo4j มีข้อมูลประมาณ 22 บริษัท 65 เอกสาร 3,576 ส่วนข้อความ และ 14,692 รายการ Entity ส่วน PostgreSQL มีข้อมูล periodic rows 4,890 รายการ จาก 26 บริษัท ตัวเลขดังกล่าวเป็นภาพรวมของข้อมูลในระบบ ณ ช่วงเวลาที่ตรวจสอบ ไม่ใช่ผลการวัดคุณภาพการสกัดข้อมูลโดยอัตโนมัติ

### 3.2 เครื่องมือค้น

ระบบมีเครื่องมือค้น 4 ประเภท

| เครื่องมือ | หน้าที่อธิบายแบบง่าย | สถานะการประเมิน |
|---|---|---|
| Vector Search | ค้นส่วนข้อความที่มีความหมายใกล้กับคำถาม | ประเมินแล้ว |
| Graph Search | ค้นโดยอาศัยรายการและความสัมพันธ์ในกราฟ | ประเมินแล้ว |
| Financial Search | ค้นตัวเลขและคำนวณจาก PostgreSQL | ประเมินแล้วในระดับ ETL และ E2E ภายใน |
| News Search | ค้นข่าวล่าสุดพร้อมวันและแหล่งที่มา | สร้างแล้ว แต่ยังไม่มี Benchmark หลัก |

### 3.3 สิ่งที่อยู่นอกข้อสรุปของรายงานนี้

รายงานฉบับนี้ยังไม่สรุปว่าระบบสกัดกราฟมีความถูกต้องสูงในทุกกรณี เพราะยังไม่มีการประเมินความถูกต้องของ Entity และความสัมพันธ์อย่างเป็นระบบ นอกจากนี้ยังไม่สรุปว่า Full Agent ให้คำตอบสุดท้ายดีกว่าวิธีเดิมในทุกประเภทคำถาม เนื่องจากการประเมิน Full Agent แบบรวม Vector, Graph, Financial และ News ยังเป็นงานต่อไป

### 3.4 การตีความขอบเขตจากเอกสารตั้งต้น

เอกสารตั้งต้นกำหนดขอบเขตข้อมูลบรรยายไว้ที่ Item 1, Item 1A และ Item 7 ของรายงาน 10-K เพื่อเน้นข้อมูลธุรกิจ ความเสี่ยง และคำอธิบายผลการดำเนินงาน ขอบเขตนี้ยังคงใช้ใน Production Graph ปัจจุบัน ส่วนตารางตัวเลขทางการเงินที่มีโครงสร้างสูงจะถูกเก็บและค้นจาก PostgreSQL แทน ไม่ได้พยายามยัดข้อมูลทุกชนิดลงในกราฟเดียว

แนวทางนี้มีเหตุผลเชิงวิศวกรรม คือกราฟเหมาะกับการเก็บ “ใครเกี่ยวข้องกับอะไร” ส่วน PostgreSQL เหมาะกับการเก็บ “ค่าเท่าไรในปีใด” การแยกหน้าที่ทำให้แต่ละฐานข้อมูลตอบโจทย์ของตัวเอง และทำให้ตรวจสอบแหล่งที่มาของคำตอบได้ง่ายขึ้น

## 4. ภาพรวมการทำงานของระบบ

การทำงานแบ่งเป็นสองช่วงใหญ่

### 4.1 ช่วงเตรียมข้อมูล

```text
รายงานบริษัท / ข้อมูลการเงิน / ข่าว
        ↓
ดึงข้อมูลและทำความสะอาด
        ↓
แบ่งรายงานเป็นส่วนข้อความ
        ↓
สร้างรายการและความสัมพันธ์ในกราฟ
        ↓
บันทึกข้อความลง Neo4j
        ↓
แปลงข้อมูลตัวเลขและบันทึกลง PostgreSQL
```

ขั้นตอนนี้ทำให้ระบบออนไลน์ไม่ต้องอ่านเอกสารต้นฉบับใหม่ทุกครั้งที่มีคำถาม และสามารถอ้างอิงกลับไปยังเอกสารหรือรายการตัวเลขต้นทางได้

### 4.2 ช่วงตอบคำถาม

```text
ผู้ใช้ส่งคำถาม
        ↓
วิเคราะห์ชนิดของหลักฐานที่ต้องการ
        ↓
เลือก Vector / Graph / Financial / News
        ↓
เก็บหลักฐานและบันทึกผลการค้น
        ↓
ตรวจว่าหลักฐานเพียงพอหรือไม่
        ↓
สรุปคำตอบพร้อมแหล่งอ้างอิง
```

ในระดับ Agent ระบบสามารถบันทึกการค้นแต่ละรอบไว้ใน Attempt Ledger ได้ หากหลักฐานไม่พอ ระบบอาจค้นซ้ำโดยใช้คำใบ้ที่เจาะจงขึ้น หรือหยุดพร้อมแจ้งว่ายังขาดหลักฐาน แทนการตอบโดยอาศัยความรู้ภายนอก

### 4.3 เส้นทาง Agent รุ่นปัจจุบัน

เอกสารตั้งต้นอธิบาย Agent ด้วยคำว่า ReAct และ Reflection เพื่อสื่อว่า Agent สามารถคิดแล้วลงมือค้น จากนั้นตรวจผลการค้นได้ แนวคิดนี้ยังคงอยู่ แต่การเขียนระบบจริงถูกจัดระเบียบใหม่ให้ดูแลและตรวจสอบได้ง่ายขึ้น

```text
PlanRoute
   ↓
Dispatcher — แยก Task ตามแผน
   ↓
Task Worker แต่ละตัวทำงานแยกกัน
   ├─ Execute Attempt
   ├─ Assess หลักฐาน
   ├─ Retry ด้วยคำใบ้หรือกลยุทธ์ที่ต่างขึ้นเมื่อเหมาะสม
   └─ Completion record ของ Task
   ↓
Collector — รวมผลตามลำดับของแผน
   ↓
Synthesis — สรุปครั้งเดียวพร้อม Citation
```

ใน Config ปัจจุบันกำหนดให้ทำงานพร้อมกันได้สูงสุด 2 Task, แต่ละ Task มีได้สูงสุด 3 Attempts, การตรวจ Assessment มีได้สูงสุด 2 ครั้ง และการลองซ้ำทางเทคนิคมีได้สูงสุด 1 ครั้ง ค่าเหล่านี้อยู่ใน Config เพื่อให้ควบคุมเวลาและตรวจสอบการทดลองได้ ไม่ได้ฝากไว้ใน Prompt เพียงอย่างเดียว

## 5. วิธีค้นกราฟและเหตุผลที่เลือกใช้

การค้นกราฟในโครงงานไม่ได้ดูเพียงว่าคำในคำถามเหมือนกับคำในข้อความหรือไม่ แต่พิจารณาว่ารายการในคำถามเชื่อมโยงกันอย่างไร

ตัวอย่างเช่นคำถามหนึ่งอาจต้องค้นเส้นทางดังนี้

```text
บริษัท
  → กลุ่มธุรกิจ
  → รายการค่าใช้จ่าย
  → ผลกระทบต่อผลประกอบการ
```

กระบวนการค้นกราฟประกอบด้วย 4 ขั้นตอนแบบย่อ

1. ระบุรายการสำคัญจากคำถาม เช่น ชื่อบริษัท ปี หรือหัวข้อทางการเงิน
2. ใช้รายการเหล่านี้เป็นจุดเริ่มต้นของการค้น
3. กระจายน้ำหนักไปตามความสัมพันธ์ที่เกี่ยวข้อง โดยให้รายการที่เชื่อมใกล้และเกี่ยวข้องมีความสำคัญมากกว่า
4. แปลงผลลัพธ์กลับมาเป็นส่วนข้อความเพื่อใช้เป็นหลักฐาน

วิธีนี้เหมาะกับคำถามที่คำตอบกระจายอยู่หลายส่วนของรายงาน แต่ส่วนต่าง ๆ มีความสัมพันธ์กัน หากคำถามเป็นการถามข้อเท็จจริงง่าย ๆ Vector Search อาจเพียงพอและใช้เวลาน้อยกว่า

### 5.1 การปรับจากวิธีที่เสนอไว้ในเอกสารตั้งต้น

เอกสารตั้งต้นอธิบายการค้นกราฟในระดับแนวคิด ได้แก่ การหา Entity จากคำถาม ใช้เป็นจุดเริ่มต้นของ PPR และแปลงคะแนนกลับมาเป็น Chunk ปัจจุบันได้ทำขั้นตอนนี้ละเอียดขึ้น โดยมีองค์ประกอบสำคัญดังนี้

- ใช้ Query-to-Triple หรือ Query-to-Entity เป็นจุดเริ่มต้นตามโหมดการทดลอง
- ใช้กราฟที่มีประเภทของรายการและความสัมพันธ์ชัดเจน เพื่อลดการเดินไปยังรายการที่ไม่เกี่ยวข้อง
- เชื่อมผลคะแนนจากรายการกลับไปยัง Chunk ผ่านความสัมพันธ์ MENTIONS
- เก็บ Trace ของ Seed, Candidate, PPR และการคัดเลือก Chunk เพื่ออธิบายผลการค้น
- ใช้ Graph projection ที่เตรียมไว้ซ้ำได้ เพื่อลดงานสร้างโครงสร้างกราฟซ้ำระหว่างคำถาม

ค่าที่ใช้ใน Freeze SOX74 Agent + Graph คือ `top_k_triples=20`, `ppr_graph_mode=entity_chunk`, `triple_filter=llm` และ `final_rerank=none` ส่วนค่าเริ่มต้นใน Config ปัจจุบันลด `top_k_triples` เป็น 10 เพื่อควบคุมเวลา การเปรียบเทียบผลต้องอ้างอิงค่าที่ถูกบันทึกใน Run Config ของแต่ละการทดลอง ไม่ใช้ค่าเริ่มต้นปัจจุบันไปตีความผลย้อนหลัง

### 5.2 การปรับวิธีสกัดกราฟ

ในเอกสารตั้งต้นวางแผนให้ GLiNER สกัด Entity และให้ LLM สกัดความสัมพันธ์ ปัจจุบันการสกัดหลักใช้ LLM เรียกเดียวเพื่อส่งกลับทั้งรายการและความสัมพันธ์ แล้วตรวจโครงสร้างด้วย Pydantic ให้ตรงกับ Schema จากนั้นมีขั้น Evidence-grounded graph repair สำหรับเติมความสัมพันธ์ที่มีประโยคในเอกสารรองรับและตัดรายการที่ไม่มีหลักฐานเชื่อมโยงเพียงพอ

การเปลี่ยนนี้เป็นการปรับจากผลทดลองและปัญหาการดูแลระบบ ไม่ใช่การเปลี่ยนโจทย์วิจัย แก่นของงานยังคงเป็นการสร้างกราฟที่มี Schema และ Provenance เพื่อนำไปค้นและตรวจสอบได้ แต่ไม่ควรกล่าวว่า GLiNER เป็นองค์ประกอบของเส้นทาง Production ปัจจุบัน

## 6. ผลการประเมิน Retrieval จาก FinReflectKG SOX74

### 6.1 วิธีการทดลอง

การทดลองใช้คำถามชุดเดียวกัน 74 ข้อ และกำหนดจำนวนหลักฐานสุดท้ายเท่ากันที่ 9 ชิ้น เพื่อเปรียบเทียบ 4 รูปแบบ

- Vector-only
- Agent + Vector
- Graph-only
- Agent + Graph

ทุกการทดลองเสร็จสมบูรณ์โดยไม่มีข้อผิดพลาดที่บันทึกไว้ และใช้คำถามในลำดับเดียวกัน รายละเอียดถูกเก็บในชุดหลักฐาน `sox74_retrieval_ablation_v1`

เพื่อให้การเปรียบเทียบยุติธรรม การทดลองใช้จำนวนหลักฐานปลายทางเท่ากันที่ 9 Chunk สำหรับทุกแบบ Non-agent คืนผล 9 Chunk โดยตรง ส่วน Agent รวมหลักฐานจากหลายรอบแล้วเลือกเข้าสู่บริบทสรุปไม่เกิน 9 Chunk แต่ละรอบการค้นของ Agent ใช้ `top_k_chunks=5`

ใน Freeze นี้ Graph ใช้ `top_k_triples=20`, โหมด `entity_chunk`, ตัวกรอง Triple แบบ LLM และไม่มี Reranker ภายนอกในขั้นสุดท้าย ผลการรันทั้ง 4 แบบใช้ 74 Query เดียวกันตามลำดับเดียวกัน และไม่มี Error ที่บันทึกไว้

### 6.2 ความหมายของตัวชี้วัด

- **Hit@9**: ในหลักฐาน 9 ชิ้น มีหลักฐานที่เกี่ยวข้องอย่างน้อยหนึ่งชิ้นหรือไม่
- **Recall@9**: จากหลักฐานที่คำถามต้องการทั้งหมด ระบบค้นพบได้กี่ส่วนภายใน 9 ชิ้น
- **Latency**: เวลาเฉลี่ยที่ใช้ตอบหนึ่งคำถาม

### 6.3 ผลลัพธ์

| รูปแบบ | Hit@9 | Recall@9 | เวลาเฉลี่ยต่อคำถาม |
|---|---:|---:|---:|
| Vector-only | 0.392 | 0.176 | 0.249 วินาที |
| Agent + Vector | 0.514 | 0.270 | 33.965 วินาที |
| Graph-only | 0.649 | 0.390 | 18.222 วินาที |
| Agent + Graph | **0.743** | **0.450** | 84.196 วินาที |

### 6.4 การตีความ

ผลการทดลองแสดงแนวโน้ม 2 ด้าน

1. Graph Search เหมาะกับคำถามหลายทอดมากกว่า Vector Search ในชุดคำถามนี้
2. Agent ช่วยให้ระบบค้นหลักฐานเพิ่มได้ โดยเฉพาะเมื่อใช้ร่วมกับ Graph
3. การเพิ่ม Agent มีต้นทุนด้านเวลา เนื่องจากต้องวิเคราะห์คำถาม ประเมินหลักฐาน และอาจค้นซ้ำหลายรอบ

ดังนั้นข้อสรุปที่เหมาะสมไม่ใช่ “Agent ดีกว่าในทุกมิติ” แต่เป็น “Agent + Graph เพิ่มโอกาสพบหลักฐาน แต่ต้องปรับปรุงเวลาให้เหมาะกับการใช้งานจริง”

### 6.5 ข้อควรระวัง

การทดลองนี้วัดคุณภาพของการค้นหลักฐานเป็นหลัก ไม่ใช่การตัดสินความถูกต้องของคำตอบสุดท้ายทั้งหมด นอกจากนี้สภาพแวดล้อมของชุด Benchmark อาจต่างจากฐานข้อมูล Production จึงต้องแยกคำว่า “ผลบนชุดทดลอง” ออกจาก “ความพร้อมใช้งานจริง”

ชุด SOX74 เป็นชุดคำถามหลายทอดที่เหมาะกับการตรวจความสามารถด้าน Graph Retrieval จึงไม่ควรใช้เป็นตัวแทนของคำถามทางการเงินทุกประเภท และไม่ควรนำผลชุดนี้ไปสรุปว่า Financial Search หรือ News Search มีคุณภาพเท่ากัน

## 7. ผลการประเมินข้อมูลทางการเงิน

### 7.1 การตรวจสอบการนำเข้าข้อมูล

ระบบนำข้อมูลตัวเลขมาเก็บใน PostgreSQL และเปรียบเทียบกับข้อมูลจาก SEC EDGAR จำนวน 370 รายการ พบรายการที่ตรงกัน 364 รายการ หรือ 98.38% รายการที่พบมีค่า หน่วย และรอบเวลาตรงกัน 100% ไม่พบ Business Key ซ้ำในข้อมูลที่ตรวจสอบ

รายการที่ขาด 6 รายการเกี่ยวข้องกับความแตกต่างของชื่อแนวคิดตัวเลขในข้อมูล XBRL จึงสะท้อนปัญหาการจับคู่ชื่อข้อมูลมากกว่าการเปลี่ยนค่าตัวเลขหลังจัดเก็บ

### 7.2 การทดสอบการตอบคำถามทางการเงิน

การทดสอบภายในมีคำถาม 60 ข้อ ครอบคลุมการค้นตัวเลข การเปรียบเทียบหลายบริษัท การดูแนวโน้มหลายปี ตัวชี้วัดที่คำนวณเพิ่ม และคำถามที่อยู่นอกขอบเขต

| รายการ | ผล |
|---|---:|
| การเลือกเครื่องมือถูกต้อง | 100% |
| การสร้างคำสั่งค้นข้อมูลถูกต้อง | 100% |
| การทำงานของ SQL | 100% |
| การดึงข้อมูลตัวเลข | 100% |
| ผ่านเกณฑ์อัตโนมัติ | 58/60 หรือ 96.67% |
| ผ่านหลังตรวจสอบความหมายโดยมนุษย์ | 59/60 หรือ 98.33% |

มีข้อผิดพลาดจริงหนึ่งกรณีที่ระบบตีความคำว่า debt-to-equity โดยใช้หนี้สินรวมแทนหนี้สินที่ตรงตามนิยาม การค้นพบนี้มีประโยชน์ต่อการพัฒนาระบบ เพราะแสดงให้เห็นว่าแม้ฐานข้อมูลและสูตรจะถูกควบคุมไว้ แต่การตีความคำถามก่อนเรียกเครื่องมือยังต้องมีการตรวจสอบเพิ่มเติม

อย่างไรก็ตาม ชุดคำถาม 60 ข้อนี้เป็นชุดทดสอบที่สร้างขึ้นภายในโครงงาน จึงควรนำเสนอเป็นผลการทดสอบภายใน ไม่ควรใช้แทนการประเมินโดยผู้ตรวจภายนอกทั้งหมด

## 8. สถานะ Agent และ Production Application

Agent รุ่นปัจจุบันมีโครงสร้างสำหรับ

- แยกคำถามเป็นงานย่อย
- เลือกเครื่องมือค้น
- บันทึกผลการค้นแต่ละรอบ
- ตรวจว่าหลักฐานเพียงพอหรือไม่
- ขอให้ค้นซ้ำเมื่อมีแนวทางที่มีประโยชน์
- สรุปหลักฐานและเก็บร่องรอยการทำงาน

ส่วนที่เปลี่ยนจากเอกสารตั้งต้นอย่างชัดเจนคือระบบไม่ได้ใช้ Observe และ Reflect แบบเดิมเป็นเส้นทางหลักอีกต่อไป แต่รวมการตรวจหลักฐานไว้ใน Assess ของ Task Worker และใช้ Attempt Ledger เป็นบันทึกกลาง การออกแบบปัจจุบันเพิ่ม Dispatcher และ Collector เพื่อให้ Task ที่ไม่พึ่งพากันทำงานพร้อมกันได้ และเรียก Synthesis เพียงครั้งเดียวหลังรวมผล

ส่วนนี้แสดงให้เห็นว่า Agent สามารถทำหน้าที่เป็นผู้ประสานงานระหว่างเครื่องมือค้นได้ แต่ยังไม่ควรสรุปว่า Full Agent พร้อมใช้งาน Production ในทุกกรณี เนื่องจากยังต้องวัด Routing, คุณภาพคำตอบสุดท้าย, ความสม่ำเสมอ และเวลาในการตอบแบบรวมทั้ง 4 เครื่องมือ

สำหรับการนำเสนอ ควรอธิบาย Agent เป็น “ชั้นควบคุมการค้น” ไม่ใช่เป็นจุดขายว่าระบบมีความฉลาดเหมือนนักวิเคราะห์มนุษย์

## 9. ผลงานและข้อกล่าวอ้างที่รองรับได้ในปัจจุบัน

เอกสารตั้งต้นเสนอประโยชน์ของโครงงานไว้ 3 ระดับ ได้แก่ ประโยชน์เชิงวิชาการ เชิงเทคโนโลยี และเชิงประยุกต์ เมื่อปรับให้ยึดหลักฐานปัจจุบัน สามารถสรุปได้ดังนี้

### 9.1 ด้านวิชาการ

- แสดงแนวทางการใช้โครงสร้างข้อมูลจาก FinReflectKG กับเอกสารบริษัทในกลุ่ม Semiconductor
- แยกการประเมินเป็นคุณภาพการค้นหลักฐานและความถูกต้องของข้อมูลตัวเลข ทำให้เห็นว่าความผิดพลาดเกิดจากชั้นใด
- เก็บผลการทดลองแบบมีข้อมูลต้นทาง คำสั่งรัน และค่า Config เพื่อให้ทำซ้ำและตรวจสอบย้อนหลังได้

สิ่งที่ควรใช้คำว่า “แสดงให้เห็น” คือผลการทดลองบน Corpus นี้ ยังไม่ควรกล่าวว่าเป็นวิธีมาตรฐานที่ใช้ได้กับทุกอุตสาหกรรม

### 9.2 ด้านเทคโนโลยี

- สร้างระบบค้นที่รวมข้อความ กราฟ ตัวเลข และข่าวไว้ในกระบวนการเดียว
- ใช้ Graph Search ที่อาศัย Personalized PageRank เพื่อเพิ่มความสามารถในการค้นข้อมูลหลายทอด
- ใช้ PostgreSQL และสูตรที่กำหนดไว้เพื่อให้การตอบคำถามตัวเลขตรวจสอบได้
- เก็บ Citation และ Trace ของการค้น เพื่อให้ผู้ใช้เห็นว่าได้หลักฐานมาจากไหน

ผล SOX74 สนับสนุนเฉพาะข้อกล่าวอ้างว่า Graph และ Agent ช่วยเพิ่มการค้นพบหลักฐานในชุดคำถามหลายทอดได้ ส่วนความเร็วและ Full Agent แบบรวมทุกเครื่องมือยังต้องปรับปรุงและประเมินต่อ

### 9.3 ด้านการประยุกต์ใช้

ระบบเหมาะกับการเป็นเครื่องมือช่วยสำรวจเอกสารและหลักฐานสำหรับนักศึกษา นักวิจัย หรือผู้วิเคราะห์ที่ต้องการย้อนกลับไปอ่านแหล่งข้อมูล ไม่ควรนำเสนอเป็นระบบให้คำแนะนำซื้อขายหรือระบบคาดการณ์ราคาหุ้น

## 11. ข้อจำกัดของโครงงานในระยะปัจจุบัน

1. ยังไม่มีการวัดคุณภาพการสกัด Entity และความสัมพันธ์จากรายงานอย่างเป็นระบบ
2. News Search ยังไม่มีชุดทดสอบที่ตรึงแหล่งข่าวและเวลาไว้อย่างเป็นทางการ
3. Full Agent ยังไม่ได้ประเมินครบทั้งการเลือกเครื่องมือ เส้นทางการทำงาน และความถูกต้องของคำตอบสุดท้าย
4. Agent + Graph ใช้เวลาสูงกว่า Graph-only อย่างมาก
5. Financial benchmark ภายในมีผลดี แต่ยังต้องมีการตรวจสอบโดยผู้ประเมินเพิ่มเติม
6. ผล SOX74 เป็นการวัดความสามารถในการค้นหลักฐานในโดเมนเฉพาะ ไม่ควรอ้างว่าใช้แทนทุกโดเมนได้
7. ระบบไม่ใช่ระบบพยากรณ์ราคาและไม่ใช่ระบบให้คำแนะนำซื้อขาย
8. แผนในเอกสารตั้งต้นที่ระบุ FinanceBench 50 ข้อ และ FinReflectKG 50 ข้อ รวม 100 ข้อ ยังไม่ใช่ชุดหลักฐานที่รายงานฉบับนี้อ้าง ผลที่ตรึงแล้วใช้ SOX74 และชุด Financial ภายใน 60 ข้อเป็นหลัก
9. ขอบเขตข่าวในเอกสารตั้งต้นระบุ 6 เดือน แต่ระบบปัจจุบันใช้ค่าเริ่มต้น 90 วัน และมี cache แบบเลือกใช้ได้เพื่อรองรับการทดลองแบบกลุ่ม
10. ขอบเขตบริษัทในเอกสารตั้งต้นระบุประมาณ 30 บริษัท แต่ Config ปัจจุบันใช้ 22 ticker จึงต้องรายงานจำนวนจริงตาม Run ที่ใช้ ไม่ใช้ตัวเลขประมาณการเดิม

การระบุข้อจำกัดเหล่านี้ช่วยให้การสรุปผลอยู่บนหลักฐานจริง และป้องกันการกล่าวอ้างเกินกว่าการทดลองที่ทำแล้ว
