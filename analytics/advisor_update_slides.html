วิธีประเมินผล Retrieval

  • Dev set N=50 — คำถาม multi-hop สังเคราะห์ ทุกข้อ verified ground truth จาก graph (ใช้ปรับจูน)
  • Held-out N=10 — ล็อกไว้ ยังไม่เปิดดู (วัด final ที่ unbiased)
  • Metrics — Hit@5, Recall@5
  • Statistical tests (paired, α=0.05):
Testวัดอะไร
McNemarHit@5 — ความต่างของผล ใช่/ไม่ใช่
Wilcoxon signed-rankRecall@5 — ความต่างของคะแนน (ไม่ assume normal)
Bootstrap 95% CIช่วงเชื่อมั่นของค่าเฉลี่ยความต่าง
Cohen's heffect size — ขนาดของผล
เน้นว่า held-out ยังไม่เปิด = ตั้งใจกัน overfit. stat test ทำให้ claim ไม่ใช่แค่ "ตัวเลขดูดีขึ้น"

ข้อจำกัดที่พบ — วิเคราะห์ตรงไปตรงมา

คำถามเปรียบเทียบ 2 บริษัท (เช่น "เทียบ GPU ของ NVDA กับ AMD") ยังตอบได้ไม่สมดุล

อาการ — retrieval ดึง chunk เอียงไปบริษัทเดียว
ตัวอย่าง: "เทียบ GPU NVDA vs AMD" → ได้ 4 AMD chunks : 1 NVDA chunk → คำตอบเอียงข้าง AMD
สาเหตุ — top-k มีจำกัด, chunk 2 บริษัทแย่ง slot กัน + hub-drift (entity ที่ frequency สูงดูดการ retrieve)
ทางแก้ — Phase D · query decomposition: แตกคำถามเป็น "NVDA GPU" + "AMD GPU" → retrieve แยก → การันตี chunk ทั้ง 2 ฝั่ง
การโชว์ failure ที่อธิบายได้ + มีทางแก้ออกแบบไว้แล้ว ดีกว่า demo ที่ดูสมบูรณ์แบบ
